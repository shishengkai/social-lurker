# Grok Bot 验收（开发完成后实际运行）

以下均需目标环境证据，不能把本地测试通过当成已验证。

1. 在 `/workspace/social-lurker/` 安装开发包并绑定实例，doctor。重启或下一次 routine 检查 SQLite、settings、.env 与过程文件持久。
2. 第二个 Bot 新 UUID、独立库；改名仍原目录，复制不沿用原实例。一个实例占锁时第二次 tick 返回 BUSY；其他实例不共享正文或 key。
3. 用户明确授权真实样本测试，分别完成视频号、抖音作品 → 下载/解密 → 完整 MP3 → fal CDN → Whisper → 原稿入库。核对上传输入的实际保留期，48 小时只是请求参数。
4. 用当前 Bot 自身 LLM 处理长于 6000 字的全文，逐段 edits；中断后只续校对，全部原文覆盖、尾部保留、原稿与校对稿可追溯。
5. 原生消息工具分别发送短文和不同长度的中文正文，确认工具能力/模型输出/UI 三处字符与尾部一致，取得真实消息 ID 和读回证据。超过上限时 blocked，不能自动分拆或生成文件。
6. 两博主三作品 → 三条独立消息；同一作品被两个 Bot 关注 → 各一条。历史 N 条包含 initial，只发结束汇总。模拟发送后 ack 前中断 → unknown，不自动重发。
7. 处理中 stop → 完成并保存，待发及后续完成通知抑制。resume 不补旧周期。delete 仅自身资料。
8. 创建当前 Bot 唯一 30 分钟 routine，至少验证一轮无更新、一轮有更新、一次中断续跑。无更新不推送；主会话是否出现执行/校对痕迹单独记录。不满足强静默时明确失败，再决策，不能另起 cron。
9. 实际稳定 Release 出现后验证精确 SHA、安装清单、版本切换、维护恢复、其他 Bot 不受影响。没有正式 Release 时不能伪称升级验收通过。

验收记录应只保存结论、时间、版本与脱敏证据；不保存 API key、签名媒体地址或文稿副本。正式启用 routine 和宣告产品可用须覆盖以上相关门槛。
